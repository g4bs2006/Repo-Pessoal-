> **Código-base:** `Agenda---Contact-` (Next.js 16.2.6 + React 19 + TS 5 + Tailwind 4 + Supabase PG17)

**Legenda de status:** 🔲 todo · 🔄 doing · 👀 review · ✅ done · ⛔ blocked
**Esforço relativo:** P (≤ ½ dia) · M (~1 dia) · G (teto de 1 dia, risco — subdividir se estourar)

**Convenções do projeto (validadas no código real):**
- Rotas API usam `withAuth(handler, allowedRoles?)`, `ok()`, `err()` de `@/lib/api`. RBAC já é suportado pelo 2º argumento de `withAuth`.
- DB via `supabaseAdmin` de `@/lib/supabase`; toda tabela tem `account_id` (multi-tenant, RLS).
- Validação de input com `zod`.
- Integração Helena centralizada em `@/lib/helena.ts` (`helenaFetch`, Bearer token via env). Status enum atual: `confirmed|in_progress|completed|cancelled|no_show`.
- Tipos do banco em `src/types/database.ts` (regenerar após cada migration).
- ⚠️ Esta versão do Next.js tem breaking changes — ler `node_modules/next/dist/docs/` antes de codar padrões novos (ver `Agenda---Contact-/AGENTS.md`).

### 1.4 Riscos ativos

- **R1 — `PUT /crm/v2/panel/card/{id}` pode não mover etapa em alguns painéis.** Mitigação: fallback duplicate/delete+create (TASK-021). Validado em produção (Salutar) mas confirmar por conta.
- **R2 — Eventos reais de webhook Helena não inventariados** (Doc 2 §9.1). Mitigação: TASK-026 (PoC) antes de codar o receiver.
- **R3 — Tags são UUIDs pré-criados manualmente na Helena** (API não cria). Bloqueia EPIC-01. Mitigação: TASK-012 (pré-requisito humano).
- **R4 — Token Helena exposto.** Risco ativo → TASK-001 (rotação) é o item #1 absoluto.
- **R5 — Prefixos de path da Helena divergentes.** O código real usa `/core/v1/...` e `/chat/v1/...`; o briefing cita `/crm/v2/...` para cards. Confirmar prefixo por endpoint na TASK-010 antes de generalizar.

### 1.5 Pendências para o analista (lacunas encontradas na decomposição)

- **PEND-1 [RESOLVIDA 15/06]:** Endpoint canônico de movimentação = `PUT /crm/v2/panel/card/{cardId}` (validado em produção no workflow Salutar). Doc 2 §3/§7 corrigido para refletir o path real; `/v3/panel-card` descartado.

## EPIC-00 — Fundação: segurança, secrets e migrations do espelho

**Objetivo:** preparar o terreno seguro e o esquema de dados antes de qualquer integração: rotacionar o token vazado, criar o cofre de credenciais por conta, criar todas as tabelas novas (espelho Helena, outbox, webhooks, mapeamentos) com RLS e estabelecer a base de RBAC.
**RFs/RNFs:** RNF-010, RNF-011, RNF-014 (estruturas), ADR 1/7/8 (infra de dados).
**Definition of Done do épico:**
- [ ] Token Helena antigo revogado e novo em secret store; nada de token em cliente/repo.
- [ ] Migrations das novas tabelas aplicadas com RLS por `account_id` e tipos regenerados.
- [ ] `account_integrations` operacional (leitura server-side apenas).
- [ ] Novas tabelas validadas por `get_advisors` (sem alertas de segurança RLS).

### STORY-0.1 — Segurança imediata de credenciais
> Como **responsável técnico**, quero **rotacionar o token Helena exposto e mover credenciais para um cofre por conta**, para **eliminar o risco de vazamento e suportar multi-tenant**.
> **RFs:** RNF-010. **Critérios de aceite:** token antigo inválido; nenhuma credencial no browser/repo; chamadas externas só do backend.

#### TASK-001: Rotacionar token Helena exposto e migrar para secret store
- **Story:** STORY-0.1 · **Requisito:** RNF-010 · **Depende de:** nenhuma · **Esforço:** P · **Senioridade:** sênior/devops · **Status:** 🔲 todo
- **Contexto:** o token Helena (`pn_...`) está exposto no workflow n8n compartilhado. É o risco de segurança #1 e deve ser o primeiro item executado.
- **Arquivos/locais envolvidos:**
  - Painel Helena (web) — gerar novo token e revogar o antigo.
  - `Agenda---Contact-/.env` e Environment Variables da Vercel — atualizar `HELENA_API_TOKEN`.
  - Workflow n8n — substituir o token hardcoded (será depreciado pelo ADR 7, mas rotacionar já).
- **Passo a passo:**
  1. No painel Helena, gerar novo token de API e **revogar o token antigo exposto**.
  2. Atualizar `HELENA_API_TOKEN` no `.env` local e na Vercel (todas as envs).
  3. Remover o token hardcoded do workflow n8n; usar credencial do n8n.
  4. Validar com `GET /core/v1/contact/phonenumber/{phone}` de teste via `@/lib/helena.ts` (deve responder 200).
  5. Confirmar que o token antigo agora retorna 401.
- **Critérios de aceite:** novo token funciona; antigo retorna 401; nenhum token em arquivo versionado.
- **Como testar:** `Invoke-RestMethod` com token antigo → 401; com novo → 200.
- **DoD:** AC atendidos · sem token no git · checkbox no painel (§5).

#### TASK-002: Tabela `account_integrations` (secrets por conta)
- **Story:** STORY-0.1 · **Requisito:** RNF-010, RNF-011 · **Depende de:** TASK-001 · **Esforço:** M · **Senioridade:** pleno/data-engineer · **Status:** 🔲 todo
- **Contexto:** cada clínica tem token Helena próprio (e futuramente credenciais Clinicorp). Doc 2 §4.2 exige secrets cifrados por conta, nunca expostos ao cliente.
- **Arquivos/migrations:** `supabase/migrations/<ts>_account_integrations.sql`
  - Tabela `account_integrations`: `id uuid pk`, `account_id uuid fk`, `provider text` (`helena`|`clinicorp`), `secrets jsonb` (cifrado), `panel_id text`, `is_active bool`, `created_at`, `updated_at`.
  - Índice único `(account_id, provider)`.
  - RLS por `account_id`; **nenhuma policy de SELECT para anon/cliente** — leitura só via `supabaseAdmin`.
- **Passo a passo:**
  1. Verificar Vault (`mcp Supabase list_extensions`); se ausente, usar `pgcrypto` (ver PEND-2).
  2. Escrever migration com a tabela + índice único.
  3. Habilitar RLS restrita a admin server-side.

  5. Migrar `HELENA_API_TOKEN` global para registro por conta (seed da conta atual).
- **Critérios de aceite:** token Helena por conta lido só server-side; cliente não consegue `SELECT`.
- **Como testar:** chamada client-side a `account_integrations` → vazio/403; `getIntegration()` server-side retorna o token.
- **DoD:** migration aplicada · `get_advisors` sem alerta RLS · helper testado.
